# Arquitectura objetivo

## Componentes

```text
React/Vite ── Supabase Auth ── JWT ── API Fastify/TypeScript
     │                                  │
     │                                  ├── PostgreSQL/Supabase (datos + RLS)
     │                                  ├── Storage privado (adjuntos)
     │                                  ├── Worker inbox/outbox/medios
     │                                  └── Worker IA
     │
Widget público ── API pública con rate limit, dominio y token hash
Meta Webhooks ─── firma HMAC, deduplicación y transacciones
```

El navegador usa Supabase solo para autenticación. Las operaciones de negocio pasan por el API. El rol `authenticated` no tiene permisos directos sobre tablas, secuencias ni funciones de negocio; RLS permanece activo como defensa adicional para cualquier acceso de servidor que no use la service role. La clave secreta/service role jamás se incorpora al bundle web.

## Identidad y tenant

- `auth.users.id` se enlaza con `public.users.auth_user_id`.
- El rol se lee desde `public.users`, no desde `user_metadata` editable por el usuario.
- Una sesión ordinaria obtiene su `company_id` exclusivamente del perfil habilitado en base de datos.
- No se acepta `X-Company-Id`. SuperAdmin solo puede entrar al espacio operativo de una empresa mediante rutas administrativas cuyo `companyId` se valida explícitamente.
- Las FKs compuestas `(company_id, id)` impiden enlazar contacto, conversación, mensaje, usuario, sesión o flujo de otra empresa.

## Entrega y automatización

Los webhooks terminan rápido después de validar firma y persistir. `received_messages` evita duplicados. Las respuestas salientes se guardan en `outbox_messages`; el worker usa reintento exponencial y cola muerta. Los binarios de Meta se descargan en otro worker y se suben al bucket privado. Los flujos visuales son una máquina de estados determinista; la IA se ejecuta fuera del request y respeta horario, asignación, solicitud humana y límites.

## Datos

- IDs heredados permanecen como `bigint generated by default as identity` para conservar referencias.
- Fechas son `timestamptz` UTC; `companies.time_zone` usa zona IANA.
- JSON funcional se almacena como `jsonb` con validación de forma en API.
- Los secretos son sobres AES-256-GCM (`v1.iv.tag.ciphertext`). Verify tokens se guardan solo como SHA-256.
- Adjuntos se guardan en Storage privado; la tabla contiene metadatos y SHA-256.
- Hay políticas de retención por empresa y auditoría sin secretos ni payloads completos.

Supabase recomienda habilitar RLS en cada tabla de un esquema expuesto y mantener la clave service role solo en servidor. Esta solución sigue ese modelo: <https://supabase.com/docs/guides/database/postgres/row-level-security> y <https://supabase.com/docs/guides/database/secure-data>.
